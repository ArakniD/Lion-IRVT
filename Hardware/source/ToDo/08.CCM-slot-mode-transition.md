## Implement a slot pre-charge balance before battery engages VoutS[0-7]

Below is a google background research in a transition example betwen an asynchronous to synchronous buck-boost mode, transitioning from a DCM to CCM mode for converter startup.

It is important that the B+ and B- Rails sensed by the C2000 VoutS[0-7] input is balanced to the V+ and V- sensed by the ADS131M08 while the battery is making contact with the ADS131M08 input, and not yet connected to the B+- rails that connect to the output capacitors of the buck boost converter. During this moment we have an oppurtunity to drive the High or Low FET in a manor to either drain or pre-charge the rails so a safe battery connection can be made.

While the slot configuation can be stopped, running, paused in either charged or discharge mode, when stopped the slot should actually be monitoring for a differential between the C2000 and ADS pathways, where when a ADS senses a votlage, that is taken as a pending battery insertion, and that the C2000 channel needs to balance to the ADS voltage, because they are seperate in this moment. This is a new state after STOPPED, which is actually "STOPPED->WAITING->MONITORING->BALANCING->READY->SOFT_START->RUNNING or PAUSED->SOFT_START->RUNNING(charging or discharging)", where monitoring is looking for a positive > 0.25V ADS pathway, and that the C2000 is reading anything > +-10% in voltage terms of the ADS pathway.

Once insertion is made, these two channels will read within 10% from C2000 to ADS and the balancing is no longer valid, BUT the circuit must soft-start between DCM to CCM.

soft-start should pre-calculate the starting duty cycle, and start up in buck mode until the average current is zero, as the current sense via the ADS is for average current detction mode (ACDM).

soft-start should utilise the per channel trip values to ensure no large reverse desired polarity current pulses,

balancing should auto engage if the slot is in WAITING mode. 

Stopped mode will not auto engage the waiting mode or soft-start, only a mode set to waiting from stopped will monitor for c2000 and ads2000 differential.

Add waiting to the mode bit-sets per slot.

Add monioring, balancing, and soft-start and ready to the status bit-set per slot.

During RUNNING, monitor for a rapid increase in VouS[0-7] from the C2000 pathway vs the ADS pathway, and if more than 20% difference occurs then call this slot in FAULT.

A trip during soft-start should pause quickly (100ms) and then re-try until success.

During balancing we are attempting to balance the C2000 voltage to the ADS131M08 voltages by driving the synch rectifier to either increase the voltage (drive high side) or decrease the voltage (drive low side)

During soft-start both C2000 and ADS131M08 volage paths are connected, so we are only attempting to start in DCM mode, by pre-tuning the duty cycle ratio, and preventing any large reverse current spikes as below.

make use of the RGBW LEDs to indicate to the user that slot is in soft start or balancing (same colour combination yellow) and then green once the slot is READY.

## google background research

Use below as background information only, not a directive.

For a 2-switch buck-boost topology (which transitions between buck mode and boost mode depending on whether \(V_{in} > V_{bat}\) or \(V_{in} < V_{bat}\)) connected to a pre-biased Lithium battery, starting up directly in CCM is highly risky. Because the battery holds a stiff voltage, turning on the synchronous rectifiers prematurely will cause massive reverse current to rush from the battery into your power stage or ground, destroying the MOSFETs or tripping an overcurrent fault.
To safely start up using the TI C2000 Digital Control Library (DCL) and Digital Power SDK, you must use an Asynchronous-to-Synchronous Transition Strategy.
Here is the exact implementation framework, control loop structure, and state machine architecture to achieve a stable CCM target.

1. The Control Loop Architecture (DCL)
For a battery application, you should utilize a Cascaded (Dual-Loop) Control Structure using the DCL's non-linear or standard controllers (such as the DCL_PI or DCL_DF22).
Outer Loop (Voltage or Charging Profile): Regulates the target battery voltage (\(V_{bat}\)) or follows a Constant Current (CC) profile. Its output provides the reference (\(I_{ref}\)) for the inner loop.
Inner Loop (Average Current Mode Control): Tracks the inductor current (\(I_{L}\)). This loop must run at the full PWM frequency (\(100\text{–}200\text{ kHz}\)) to quickly catch current spikes.
      +-------------+  I_ref   +-------------+  Duty
------>|  Outer Loop |--------->|  Inner Loop |---------> [PWM Generation]
 V_ref |  (DCL_PI)   |   I_L    | (DCL_DF22)  |   (EPWM)  (Force Action Qualifier)
       +-------------+          +-------------+


2. State Machine for Pre-Biased Battery Startup
You must implement a software state machine in your C2000 code (typically executed in a background task or a slow ISR) to sequence the hardware safely.
State 0: Pre-Check & Sensing
Action: Keep all PWM outputs completely low (EPWM_setActionQualifierAction forced low).
Validation: Read the ADC channels for \(V_{in}\) and \(V_{bat}\).
Crucial Step: Initialize your DCL loop integrators to prevent windup. The initial duty cycle feedback must match the battery's pre-biased state:
\(\text{Buck\ Mode\ Initial\ Duty\ }(D)\approx \frac{V_{bat}}{V_{in}}\)
\(\text{Boost\ Mode\ Initial\ Duty\ }(D)\approx 1-\frac{V_{in}}{V_{bat}}\)
Set the DCL controller clamp limits tightly around this initial guess.
State 1: Diode Emulation Mode (DEM) / Soft-Start
Action: Enable only the primary modulating switch. Do not fire the synchronous rectifier switch. Let its body diode (or a parallel Schottky) handle freewheeling.
If Bucking: Modulate the High-Side switch; keep Low-Side Sync switch off.
If Boosting: Modulate the Low-Side switch; keep High-Side Sync switch off.

Execution: Gradually ramp up the inner current reference (\(I_{ref}\)) using a software ramp function. The system operates strictly in Discontinuous Conduction Mode (DCM). Because the synchronous rectifier is off, current can never flow backward out of the Lithium battery.
State 2: Zero-Cross Alignment & CCM Transition
Action: Once the inductor current ramp ensures that the average current is comfortably positive (\(I_L > I_{CCM\_boundary}\)), you prepare to engage the synchronous rectifier.
Transition Trigger: Do not switch blindly. Wait until the output voltage matches or slightly exceeds the battery voltage, or until a fixed soft-start period expires where \(I_{L}\) is verified positive across the entire switching cycle.
Execution: Reconfigure the C2000 DB (Dead-Band) Module to enable the complementary PWM output.

3. C2000 ePWM & DCL Implementation Code
Below is a structured template showing how to configure the C2000 ePWM modules for Diode Emulation Mode and how to invoke the DCL updates in your Interruption Service Routine (ISR).
c
#include "dcl.h"

// Define Control Structures globally
DCL_PI outer_loop_pi = PI_DEFAULTS;
DCL_DF22 inner_loop_df22 = DF22_DEFAULTS;

// Global variables for system states
typedef enum {
    STATE_OFF,
    STATE_DIODE_EMULATION,
    STATE_SYNCHRONOUS_CCM
} SystemState;

SystemState current_state = STATE_OFF;
float32_t v_bat_adc, v_in_adc, i_l_adc;
float32_t i_ref_target = 2.0; // Target 2 Amps for example
float32_t i_ref_ramp = 0.0;

// High-frequency Control Loop ISR (Running at PWM frequency)
__interrupt void epwm1_isr(void)
{
    // 1. Read ADC sensors and normalize to physical values
    v_bat_adc = (float32_t)AdcaResultRegs.ADCRESULT0 * ADC_SCALE_V;
    v_in_adc  = (float32_t)AdcbResultRegs.ADCRESULT0 * ADC_SCALE_V;
    i_l_adc   = (float32_t)AdcaResultRegs.ADCRESULT1 * ADC_SCALE_I;

    switch(current_state)
    {
        case STATE_OFF:
            // Force PWM pins low securely using Action Qualifier software forcing
            EPwm1Regs.AQSFRC.bit.OTSFA = 1; 
            EPwm1Regs.AQCSFRC.bit.CSFA = 0x1; // Force Low
            break;

        case STATE_DIODE_EMULATION:
            // 2. Linear ramp for the current reference to prevent inrush
            if (i_ref_ramp < i_ref_target) {
                i_ref_ramp += 0.001f; // Slow increment per cycle
            }

            // 3. Execute Control Loops
            // In a real application, an outer loop might generate i_ref_ramp. 
            // For startup, we directly feed the ramp to the inner loop.
            float32_t current_error = i_ref_ramp - i_l_adc;
            float32_t duty = DCL_runDF22(&inner_loop_df22, current_error);

            // 4. Update PWM Compare Register
            uint16_t cmp_val = (uint16_t)(duty * (float32_t)EPwm1Regs.TBPRD);
            EPwm1Regs.CMPA.bit.CMPA = cmp_val;

            // Transition Condition: Current is stably above DCM boundary
            if (i_l_adc >= 1.5f && i_ref_ramp >= i_ref_target) {
                // Engage Synchronous CCM
                EALLOW;
                // Enable Dead-Band sub-module to generate complementary PWM on EPWM1B
                EPwm1Regs.DBCTL.bit.OUT_MODE = DB_FULL_ENABLE; 
                EDIS;
                current_state = STATE_SYNCHRONOUS_CCM;
            }
            break;

        case STATE_SYNCHRONOUS_CCM:
            // Standard Closed-Loop Average Current CCM operation
            float32_t error_ccm = i_ref_target - i_l_adc;
            float32_t duty_ccm = DCL_runDF22(&inner_loop_df22, error_ccm);
            
            EPwm1Regs.CMPA.bit.CMPA = (uint16_t)(duty_ccm * (float32_t)EPwm1Regs.TBPRD);
            break;
    }

    // Clear ISR flags
    EPwm1Regs.ETCLR.bit.INT = 1;
    PieCtrlRegs.PIEACK.all = PIEACK_GROUP3;
}

Use code with caution.
4. Critical Hardware-Software Safety Features
Dead-Band Configuration (C2000 DB Module): When transitioning to STATE_SYNCHRONOUS_CCM, ensure EPwm1Regs.DBRED (Rising Edge Delay) and EPwm1Regs.DBFED (Falling Edge Delay) are properly set before changing OUT_MODE. A shoot-through event during transition will bypass the battery protection circuitry and damage the board.
Pre-bias Anti-Windup Injection: Before moving from STATE_OFF to STATE_DIODE_EMULATION, manually force the internal state variables of your inner_loop_df22 structure to match the pre-bias duty cycle. For instance, preload the integrator state inner_loop_df22.x1 so that the first duty cycle output does not start at 0% or 100%, but directly matches \(\frac{V_{bat}}{V_{in}}\).
Analog Comparator Subsystem (CMPSS): Do not rely purely on the software DCL loop to handle startup faults. Configure an internal C2000 CMPSS module to monitor \(I_{L}\). Map the CMPSS output directly to the ePWM Trip Zone (TZ) module. If a reverse current spike exceeds your safety threshold during transition, the hardware will trip and shut down the PWMs in nanoseconds, completely bypassing the software loop.

## 1. Sanity check of the proposed logic

### 1.1 The core premise holds

> "when stopped the slot should actually be monitoring for a differential
> between the C2000 and ADS pathways"

**This works, and needs no new acquisition.** Both sense paths already run
unconditionally for every slot regardless of run state:

- `BTS_storeValuesAds()` is called from `BTS_runISR_ch1_4/5_8` on every
  ADS131M08 DRDY interrupt, with no `enable_logic` or `slotIsRunning()` gate.
- The internal ADC sweeps at 99.67 kSPS and CLA1 filters every sweep; nothing
  in the CLA task is gated on run state either.

So a STOPPED slot already has live, independently calibrated readings on both
paths:

| Path | Field | Calibration | Published as |
|---|---|---|---|
| Internal 12-bit ADC | `BTS_measValues[ch].CellVoltage_V` | `F28V_Gain` / `F28V_Offset` | `cpu1Status.cellVoltage[]` |
| ADS131M08 | `BTS_measValues[ch].Vsense_V` | `VoutGain_V` / `VoutOffset_V` | `cpu1Status.senseVoltage[]` |

**The two paths are separately calibrated**, which is what makes a differential
comparison meaningful — but also means an uncalibrated slot will show a false
differential. See Q6.

### 1.2 The state sequence is sound, with one correction

The brief writes:

> STOPPED -> WAITING -> MONITORING -> BALANCING -> READY -> SOFT_START ->
> RUNNING

As a *sequence* this is right. As *states* it is one more than necessary:
**WAITING and MONITORING cannot be distinguished by any observable.** The
moment a slot is armed it is, by definition, watching the ADS path — there is
no intermediate condition where it is armed but not yet looking. The brief
itself says "balancing should auto engage if the slot is in WAITING mode",
which confirms they are one state.

Recommendation: collapse to **WAITING** (armed and watching) and keep
MONITORING out of the status word. This matters because status bits are nearly
exhausted — see §4.

### 1.3 A real ordering problem: READY is not stable

The brief has BALANCING -> READY -> SOFT_START, where READY means "rails
matched, safe to insert". But:

- Balancing drives the rail to match the ADS reading **of a battery that has
  not yet connected**.
- The output capacitor then sits charged with **no load**.
- Between READY and physical insertion, the rail drifts — leakage, self
  discharge of the cap, the divider network itself.

So READY is not a latch, it is a *continuously re-verified* condition. If the
operator takes thirty seconds to seat the cell, the rail must still match at
the moment of contact.

Recommendation: READY is a **status bit that can clear**, and the controller
returns to BALANCING whenever the differential re-opens. The state machine is
therefore a loop, not a line:

```
STOPPED --(mode WAITING)--> WAITING
                              |
                    ADS > 0.25 V detected
                              v
                          BALANCING <---------+
                              |               |
                     |dV| within tolerance    | differential re-opens
                              v               |
                            READY ------------+
                              |
                  insertion detected (both paths agree AND
                  current path shows a real load)
                              v
                         SOFT_START
                              |
                      average current >= 0
                              v
                           RUNNING
```

### 1.4 The insertion-detection criterion is ambiguous

The brief says:

> "Once insertion is made, these two channels will read within 10% from C2000
> to ADS and the balancing is no longer valid"

But **that is the same condition as a successful balance.** If balancing has
just driven the rail to match the ADS voltage, the two paths agree — and
nothing has been inserted. Voltage agreement alone cannot distinguish "I
balanced successfully" from "a cell is now connected".

This is the single most important logical gap in the brief. Candidate
discriminators, none of which the brief specifies:

1. **A current step.** On contact, the balanced rail and the cell equalise
   through the contact resistance. Even a well-matched pair produces a
   transient. A sustained non-zero current with the converter idle is strong
   evidence of a connection.
2. **Rail stiffness.** Before insertion the rail is a capacitor — stop driving
   and it droops. After insertion it is a cell — stop driving and it holds.
   A deliberate, brief probe could test this, but it drives the stage at a
   moment we are trying to be gentle.
3. **A mechanical signal.** None exists in the firmware today.

See Q1 — this needs an answer before implementation, because the whole
sequence hinges on it.

### 1.5 "Drive the high or low FET to drain or pre-charge" — confirmed feasible

The hardware supports this, but **not** the way the background research
describes. Checked in `bts_hal.c`:

- The dead-band submodule is **not** in complementary mode. RED takes its
  input from EPWMA and FED from EPWMB (`bts_hal.c:1103-1106`), so **A and B
  are independently commanded**, with dead-band applied to each edge.
- `BTS_HAL_updateDuty()` writes `dutyH_pu` to CMPA and `dutyL_pu` to CMPB as
  two independent values.

So diode emulation does **not** require reconfiguring `DBCTL.OUT_MODE` as the
pasted TI example does. Holding the synchronous rectifier off is a matter of
forcing one output via `EPWM_setActionQualifierContSWForceAction()` — which
`BTS_ctrlDirection()` already does today for reverse-current protection.

**This is good news:** the mechanism exists, is already used, and does not
need the risky dead-band reconfiguration the research warns about.

### 1.6 A pre-existing defect sits directly under this work

`BTS_ctrlDirection()` (`bts.h:559-597`) computes per-FET duties in four
branches — and then **unconditionally overwrites both** on the last two lines:

```c
    ctrlLoopVariable->dutyH_pu = ctrlLoopVariable->dutySet_pu;
    ctrlLoopVariable->dutyL_pu = ctrlLoopVariable->dutySet_pu;
```

Every branch above is discarded. The action-qualifier forcing still takes
effect, so the FET is still held, but the duty asymmetry the function computes
is thrown away. This predates all current work (`d184a22`).

**It is load bearing for this feature**, because soft-start needs exactly the
asymmetric-duty path this function tries and fails to provide. See Q2.

### 1.7 Timing: the brief's latencies are not currently achievable

This is the hardest constraint in the whole plan.

| Requirement in the brief | Natural home | Actual rate |
|---|---|---|
| 100 ms soft-start trip retry | C1 | **~1.45 s measured** |
| 20% divergence -> FAULT while RUNNING | C1 | **~1.45 s measured** |
| Insertion detection | C1 | **~1.45 s measured** |

`C1()` is nominally 6.67 Hz and was **measured on hardware at 0.69 Hz** — the
whole A/B/C chain runs ~9x below nominal and the cause is still open (see
project note `bts-cpu1-task-chain-runs-slow`). `serviceTermination()` already
carries a comment acknowledging this.

A 1.45 s response to a rail excursion during a battery insertion is not
protection. Options:

- **A tasks** (`A1`-`A3`, nominal 1 kHz, measured ~124 Hz): ~8 ms. `A1`
  already walks all eight slots calling `BTS_updateReference()`.
- **B tasks** (nominal 200 Hz): `B1()` is **completely empty** today — a
  natural home for a mid-rate supervisor.
- **The control ISR** (ADS131M08 DRDY rate): microseconds, but every added
  branch costs eight slots' worth of ISR time at the sample rate.
- **CMPSS hardware comparators**: nanoseconds, bypassing software entirely —
  already wired to the trip zones for over-current.

Recommendation: put the fast divergence check in the control ISR or B1, not
C1. See Q3.

### 1.8 Grouped modes cannot balance per slot

`BTS_runSlot()` gives a follower the leader's `dutySet_pu`/`dutyH_pu`/
`dutyL_pu` verbatim — followers run no control loop of their own. In a grouped
MODE strap (pairs, quads, octet) the members share one converter command.

Per-slot rail balancing to a per-slot ADS voltage is therefore **structurally
impossible** in a grouped mode without restructuring `BTS_runSlot()`. Also,
`modeCallback()` silently discards any command addressed to a follower.

The brief does not mention grouping. See Q4.

### 1.9 The LEDs are not RGBW, and the requested colours collide

The brief asks for RGBW indication, yellow for balancing/soft-start and green
for READY. Against the firmware:

- **The LEDs are 3-byte GRB (WS2812B)**, not RGBW. `LED_BUFFER_SIZE` is 24
  bytes for 8 LEDs, stride `ledBuffer[ch * 3]`, every colour table is
  `uint16_t[3]`. If the hardware really is SK6812-RGBW, the existing driver is
  already misaligned and that is a separate defect to fix first. See Q7.
- **Green is already the idle colour** and the final fallback in
  `LEDDriver_update()`. Solid green for READY would be indistinguishable from
  an untouched slot.
- Yellow is free on the unit's LEDs, but on the **ESP32 display** yellow is
  already the CHARGE badge.
- **The LED driver is compiled out in the current tree.** `BTS_DEBUG_CONSOLE`
  is `true`, which forces `BTS_LED_DRIVER_ENABLED` false. Enabling the LEDs
  means giving up the AT console — they contend for GPIO29. So LED behaviour
  cannot be observed on the same build that can be probed interactively.

### 1.10 Smaller observations

- **`BTS_detectEnable()` is called but never defined.** `bts.h` calls it from
  eight sites, guarded by `BTS_ENABLE_DETECT_CODE`, which is `false`. It is a
  vestigial hook for exactly this feature — the name suggests insertion
  detection was once planned. Worth reusing the hook rather than inventing a
  parallel one.
- **`slotFinish()` leaves `stopped` clear**, so `status[].stopped` is not a
  reliable "idle" predicate. A new state machine must not assume it.
- **`slotStop()` never clears `charging`/`discharging`**, so a stopped slot
  retains a direction bit. This already makes the LED `FINISHED` branch
  unreachable — a latent bug the new states would sit on top of. See Q8.
- **Status bits are nearly exhausted.** Bits 0-18 used, ceiling at **bit 23**
  (the word crosses to CPU2 as a float32, exact only to 24 bits). Free: 16,
  19, 20, 21, 22, 23 — **six**. The brief asks for WAITING, MONITORING,
  BALANCING, SOFT_START, READY = five, leaving one. Collapsing
  WAITING/MONITORING (§1.2) leaves two.

## 3. Proposed state model

| State | `status[]` | Converter | Entered from | Left when |
|---|---|---|---|---|
| STOPPED | stopped=1 | off | anything | mode WAITING written |
| WAITING | waiting=1 | off | STOPPED | ADS > `BTS_INSERT_DETECT_V` (0.25 V) -> BALANCING; or mode 0 -> STOPPED |
| BALANCING | waiting=1, balancing=1 | **driving, no cell** | WAITING, or READY on drift | within tolerance -> READY; timeout -> FAULT |
| READY | waiting=1, ready=1 | off (rail parked) | BALANCING | insertion (Q1) -> SOFT_START; drift -> BALANCING |
| SOFT_START | running=1, softStart=1 | DCM, sync rect held off | READY, or RUNNING after a trip retry | avg current >= 0 -> RUNNING; trip -> 100 ms pause, retry |
| RUNNING | running=1 | CCM | SOFT_START | existing paths |

Transitions out of BALANCING and SOFT_START both need a **timeout to FAULT** —
the brief does not give one. See Q5.

## 10. QUESTIONS FOR REVIEW

**Q1 — How is insertion actually detected?** (§1.4, blocking)
Voltage agreement cannot distinguish "balanced successfully" from "cell
inserted" — they are the same reading. What is the discriminator? A sustained
current with the converter idle? A rail-stiffness probe? Something mechanical?
*This blocks the whole sequence.*
> ANSWER: because the output capacitors of the converter are after the current sense resistor, 
the circuit only detects current generated by the switching FETs, not any discharge or charging 
of the fets by an external connection. Balaced successfully has to be matching voltages and zero current,
while the balancing is happening the converter must charge the output capacitors to match
the incoming Vsense voltage. There is no mechanical check, and IF the Vsense and Vcellvoltage match,
then no balancing is required as they match already. 

**Q2 — `BTS_ctrlDirection()`'s last two lines discard every branch above.**

**Q4 — Do these states apply in grouped modes?** (§1.8) Followers share the
leader's duty, so per-slot balancing is impossible without restructuring.
Refuse WAITING in grouped modes, balance only the leader's rail, or restructure

> ANSWER: In these grouped connections, the outputs are connected in parrallel physically,
thus the leader can action the balancing action as it will be connected to all

**Q10 — How should the existing supervisors treat a balancing slot?** (§7)

> ANSWER: treat it as pre-running, all protections should be valid. too high current trips,

## Changelog - IMPLEMENTED 2026-10-02

All twelve questions answered by the user; implemented against those answers.

### What Q1's answer changed

The blocking question was how to tell "balanced successfully" from "cell
inserted", since both read as matching voltages. **The output capacitors sit
after the current sense resistor**, so the shunt only sees current the
switching FETs produce - never charge moving between cell and rail through
the contacts. That makes it decidable: matched + zero current is a balanced
empty rail, matched + current flowing is a connected cell. No stiffness probe
and no mechanical signal needed.

### Built

- **States**: WAITING (16), BALANCING (19), READY (20), SOFT_START (21), and
  mode bit `BTS_MODE_WAITING` 0x20. MONITORING collapsed into WAITING - an
  armed slot is by definition watching, and only bits 22/23 now remain.
- **Supervisor** in B1, which was empty and runs faster than any C task.
- **Balancing** drives a slew-limited duty toward the ADS reading, clamped to
  0.15 pu - charging capacitance needs very little, and a low ceiling bounds
  what a bad differential could ask for.
- **Soft start** holds ~100 ms on a trip and retries, 40 attempts before
  faulting, then clears back to WAITING when the cell is removed.
- **Divergence fault** at 20% for three passes stops the slot and its group.
- **LEDs**: yellow flashing while balancing or soft starting; green flashing
  at 500 ms for READY - flashing because solid green is already idle.
- **WAITING persists** across a power cycle via `BTS_STATE_F_WAITING`. The
  F-RAM per-slot flags widened 3 bits -> 4, which fills `restoreFlags`
  exactly: a fifth flag needs a wider carrier, not another bit.
- **Hosts**: decoded booleans through bts_link, test_engine, web API, BLE
  (proto 6 -> 7, four bytes appended at the end) and the display, which shows
  BAL / SS / RDY where the CC/CV tag sits.

### Two fixes the user authorised

**Q2 - `BTS_ctrlDirection()`** computed per-FET duties in four branches and
then overwrote both unconditionally on its last two lines, discarding every
branch. The action-qualifier forcing still fired, so the protection appeared
to work and only the duty shaping was lost. Present since `d184a22`. Removed,
because soft start needs exactly that asymmetric path.

**Q8 - `slotStop()`** never cleared the direction bits, so a stopped slot kept
whichever direction it last ran. That made the LED FINISHED branch unreachable
for any slot that had run, and showed a direction on an idle slot. Cleared on
stop; a pause still keeps them deliberately, because a resume needs to know
which way to go.

### Q3 corrected a stale memory of mine

I had planned around C1 running at 0.69 Hz. **Re-measured on hardware: 85.9 Hz
C dispatch, 28.6 Hz per sub-task** - 41x faster and above nominal, consistent
with the missed-clock-detection fix the user described. The memory note has
been corrected. B1 is still the right home for a 100 ms timebase, so the
placement stands; the reasoning for it does not.

### Build mode switched to production

`BTS_DEBUG_CONSOLE` false, since the AT console now lives on the ESP32. This
enables the WS2812B LED string **and** channel 1's GPIO trip input, which the
console build has to leave disconnected.
