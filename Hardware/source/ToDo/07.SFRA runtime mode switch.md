## Enable SFRA at runtime from the MODE strap, instead of compiling it out

Deferred from ToDo 06, which completed the slot-tuning registers. This is the
other half: making SFRA selectable on a running unit rather than a build-time
`#define`.

## BLOCKED - the mode table has a conflict to resolve first

ToDo 06 states MODE `0b000` is unused and should select SFRA. The code
disagrees, in a way that matters:

- `registers.h:1032` maps mode 0 to `eModeIndependent` - 8 independent slots.
  It is a real, documented mode, and the low two bits of the mode carry the
  group size, so 0 is structurally "group of 1".
- The MODE and ENABLE straps are **pulled high**, so an unstrapped board reads
  `0b111`, which `truth_table[7]` in `bts_hal.c` maps to **0**. The comment on
  that entry says "Input 0=L or ALL OFF".

So mode 0 is simultaneously the independent-slots mode and the value an
unstrapped unit boots with. **Assigning SFRA to it would put every unstrapped
board into calibration mode at power-on**, with the AT console replaced by the
SFRA serial port and no slot running.

Decide one of:

1. Give SFRA a different MODE value and leave 0 as independent-slots.
2. Re-map the truth table so the unstrapped default is a safe mode other
   than the SFRA one.
3. Require SFRA mode to be confirmed by something beyond the strap - an EN
   combination that cannot occur unstrapped, or a register write.

## Then, the implementation

- `BTS_SFRA_ENABLED` is currently a compile-time `#define (false)` read at ~20
  `#if` sites, including the injection points inside `BTS_ctrlISR()`
  (`bts.h:574`, `:620`, `:670`) and the ISR wiring in `bts_cpu1.c` and
  `bts_hal.c`. A runtime switch means the injection has to compile in
  unconditionally and be gated on a variable, which puts a branch in the
  control ISR - measure the cost before committing to it.
- SFRA takes **SCIA**, which is also the AT console (`BTS_CONSOLE_ENABLED`)
  and, in a production build, the WS2812B LED driver's output. All three
  cannot hold it at once; the switch has to hand the port over and back.
- The slot under calibration is selected by the EN straps, per ToDo 06.
- `BTS_SFRA_CAPTURE_SETTINGS` is already defined for the CCCV branch (done in
  ToDo 04), so the SFRA block will compile once enabled. `VSET_VOUT` is the
  capture point chosen for a voltage loop.
- The results of a sweep are computed externally and written back through the
  slot-tuning registers at 1068-1116, which already exist and persist - that
  half is done.

## Verification

Both cores via `buildProject` / the approved gmake, both maps checked, and the
ESP32. On hardware: that entering SFRA mode does not disturb a running slot,
and that leaving it restores the console.

## Changelog - COMPLETE

**Status: DONE.** Compile-verified on both cores, in BOTH build flavours.
**No hardware.**

### The mode-table conflict: resolved by the user

The user's decision, recorded in the resume note: repurpose
`eModeQuadsIntAdc` (6) and `eModeOctetIntAdc` (7) as the two SFRA modes and
**leave mode 0 alone**.

That is the safe resolution. Mode 0 is what an unstrapped board reads - MODE
and ENABLE are pulled high, `0b111` goes through `truth_table[7]` to 0 - so
taking it for SFRA would have put every unstrapped unit into a calibration
sweep at power-on. The tuning modes now sit where they need a deliberate
strap.

Two modes rather than one because a sweep has to run against whichever
converter closes the loop being tuned: 6 is the internal-ADC loop, 7 the
ADS131M08 loop. The grouped internal-ADC modes they replaced were never used.

### The bit-field assumption had to be broken - deliberately

Modes 0-5 encode group size in the low two bits and the converter in bit 2,
and both mode macros were pure bit arithmetic over all eight values. Left
alone they would have been **silently wrong** for the new modes:

- `BTS_MODE_GROUP_SIZE(6)` would have been 4 and `(7)` 8 - the old
  quads/octet meanings. A sweep drives ONE slot, so `BTS_HAL_setupGroupPhase()`,
  `BTS_HAL_setupTripRouting()` and `BTS_GROUP_LEADER()` would each have been
  configured for a grouping the sweep does not use: interleaved ePWM phases,
  trips routed to a leader, and followers mirroring a duty that the injection
  is actively perturbing. **Forced to 1.**
- `BTS_MODE_USES_INT_ADC()` tested bit 2, which both new modes have set - so
  mode 7 would have claimed the internal ADC while sweeping the ADS131M08
  loop. The sweep would have been injected into one loop and measured on the
  other, producing a plausible-looking Bode plot of nothing. **Now an explicit
  test.**

Verified across all eight values: 0-5 unchanged, 6 = group 1 + internal ADC,
7 = group 1 + ADS131M08.

### Runtime switch

`BTS_SFRA_ENABLED` still decides whether the SFRA **library** is compiled in -
the library, its five sweep arrays and the GUI comms are real flash and RAM,
and a production unit has no reason to carry them. What is no longer a build
switch is whether a sweep **RUNS**.

`BTS_SFRA_IS_ACTIVE()` is `btsSfraActive != 0` in a tuning build and the
literal `0` in a production one, so **a production binary carries no test at
all** in its control ISR - every guarded branch collapses at compile time. The
three injection points in `BTS_ctrlISR()` moved from `#if` to a runtime `if`.

One tuning binary now serves every slot and both loops, instead of needing a
rebuild per sweep. Strapped to a normal mode it behaves exactly like a
production unit.

`btsSfraSlot` takes the slot under test from the ENABLE straps, which
normally name the highest enabled slot; in a tuning mode there is only one.

### SCIA ownership - the part that constrains the design

SCIA is contended **four** ways: CPU2's AT console, CPU2's WS2812B LED driver,
channel 1's GPIO trip on GPIO28, and CPU1's SFRA GUI. The existing comment
already said "They cannot both have it", and `SysCtl_selectCPUForPeripheral()`
is a one-shot boot-time write.

CPU1 now keeps SCIA **only when the straps selected a tuning mode**; otherwise
it hands it to CPU2 exactly as before. This is precisely why the selection
rides on the MODE strap - itself latched once at reset - rather than on a host
register: the ownership cannot be changed while the unit runs, so a register
that "enables SFRA" at runtime could never have worked.

`btsSfraActive` is latched in `main()` immediately after the straps are read
and before anything branches on it - the CPUSEL decision, the grouping init
and the ePWM phase setup all depend on it.

### Verification

- **CPU1 in the production configuration** (`BTS_SFRA_ENABLED false`): clean.
- **CPU1 with SFRA compiled in**: also clean and linked. This is the build
  that actually exercises the new runtime gating - the production build
  compiles none of it - so it was checked explicitly rather than assumed. Only
  diagnostic is the pre-existing intentional `#warning "SFRA IS ENABLED BY
  DEFINITION"`.
- `bts_user_settings.h` restored to `(false)` afterwards; confirmed.
- CPU2 via the approved gmake: linked.
- All eight shared symbols identical in both maps; message RAM unchanged at
  `CPU2TOCPU1RAM` 0x2d0 used / 0x130 free.
