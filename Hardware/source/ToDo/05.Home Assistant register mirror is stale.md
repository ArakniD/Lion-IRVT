## Update the Home Assistant integration's register mirror to the v2.1 map

`lion-lvrt-integration`'s register mirror is still a transcription of the **v1**
map. The C2000 moved to v2 (2026-09-19) and then compressed the settings block
(v2.1, 2026-09-22); neither reorder reached this file. The ESP32's own mirror
(`esp32-btle-proxy/.../bts_regs.h`) **was** updated and is a correct reference
for everything except its stale header comment.

Found while implementing ToDo 01. Out of that ToDo's scope, recorded here
rather than fixed in passing.

### Severity

**The integration cannot currently read any unit-level register correctly.**
Every unit address it holds is 192 bytes high, so a read of `eUnitState` lands
on `eCh6_VoutOffset_pu` and returns a calibration coefficient as a state enum.
Settings reads are worse: the stride is wrong as well as the base, so a
per-slot settings read walks off into another slot.

17 tests in `tests/test_registers.py` already fail on this. They are correct
and the mirror is wrong - **do not adjust the tests to match the mirror.**

### What is wrong

| Constant | Mirror holds | C2000 has |
|---|---|---|
| `UNIT_BASE` | 1152 | **960** |
| `SET_STRIDE` | 96 | **72** (18 registers, not 24) |
| `TOTAL_REGISTERS` | 315 | **267** |
| `TOP_ADDRESS` | 1256 | **1064** |
| every `REG_*` unit address | 1152-1256 | **960-1064** |

The runtime block is unaffected: base 0, stride 48, 12 registers per slot in
both.

The settings block lost six registers per slot in the v2.1 compression, which
is where the stride change comes from. Charge and discharge limits were merged
into one pair, and the minimum cell temperature was dropped:

| Mirror offset | C2000 offset |
|---|---|
| `SET_MODE` 0 | 0 |
| `SET_CHARGE_V_MIN` 4, `SET_DISCHARGE_V_MIN` 12 | merged to `V_MIN` **4** |
| `SET_CHARGE_V_MAX` 8, `SET_DISCHARGE_V_MAX` 16 | merged to `V_MAX` **8** |
| `SET_CHARGE_I_MIN` 20, `SET_DISCHARGE_I_MIN` 28 | merged to `I_MIN` **12** |
| `SET_CHARGE_I_MAX` 24, `SET_DISCHARGE_I_MAX` 32 | merged to `I_MAX` **16** |
| `SET_MIN_CELL_TEMP` 36 | **removed** |
| `SET_MAX_CELL_TEMP` 40 | **20** |
| `SET_CAL_FIRST` 44 | **24** |

The 12 `CAL_*` offsets keep their internal order and stay relative to
`SET_CAL_FIRST`, so those do not change.

### Scope

- `custom_components/lion_lvrt/protocol/registers.py` - the mirror itself.
- Anything that indexes it. The merged charge/discharge limits mean a caller
  that wrote `SET_CHARGE_V_MAX` and `SET_DISCHARGE_V_MAX` separately now has
  one register to write, which is a **semantic** change, not just an address
  change - check `coordinator.py`, `number.py`, `sensor.py` and the config
  flow for callers that assume the two are independent.
- `tests/simulator/unit.py` if it models the settings block by offset.
- `tools/` and any HA-side documentation carrying addresses.

### Authority

`registers.h` is authoritative. Fix the mirror against it, never the reverse.
`esp32-btle-proxy/.../bts_regs.h` is a correct second opinion for the address
values, but note the two files use **different conventions** for the same
identifier families - the ESP32 uses byte offsets and bit masks where the
C2000 uses register indices and bit positions. Copying a line between them
compiles and is silently wrong. See the collision table in
`Docs/api-specification.md` §2.11.

`esp32-btle-proxy/.../bts_regs.h:53` still comments "unit mixed base 1152"
while its own `BTS_UNIT_BASE` is 960. The comment is stale, the value is
right; fix the comment while here.

### Verification

`tests/test_registers.py` must pass in full - it checks the mirror against the
C2000 enum address by address, which is exactly the drift that caused this.
Then the whole suite.

No hardware is required to fix or verify this.

## Changelog - COMPLETE

**Status: DONE.** Full test suite green: **106 passed, 16 skipped** (the skips
are Home-Assistant-absent guards). The 17 failures this ToDo cited are gone.

### The numbers were one revision staler than this ToDo said

This file was written before ToDo 06 added the slot-tuning block, so its own
table was out of date by the time it was actioned. Corrected against the
firmware:

| Constant | Mirror held | ToDo 05 said | **Actual** |
|---|---|---|---|
| `TOTAL_REGISTERS` | 315 | 267 | **280** |
| `TOP_ADDRESS` | 1256 | 1064 | **1116** |
| `UNIT_BASE` | 1152 | 960 | 960 |
| `SET_STRIDE` | 96 | 72 | 72 |

The firmware side was verified mechanically rather than by eye: all 280
registers satisfy `byte_address == index * 4`, the map is fully dense, and
`regConfig[]`/`uartRegConfig[]` agree with the enum entry for entry.

### The merge was the real work

Updating addresses was mechanical. The charge/discharge limits merging into
one direction-agnostic pair was **semantic**, and it reached further than the
mirror:

- `ChannelLimits` carried ten fields and `as_writes()` emitted eight
  addresses, of which four were duplicates after the merge - the later write
  silently winning, with no error and no read-back on that path. Cut to five
  fields. The old field names were **removed rather than aliased**, so a
  stale caller fails loudly instead of quietly writing the wrong register.
- `number.py` created **two Home Assistant entities per merged register**.
  Not a cosmetic duplicate: each caches its own value and reads back after a
  write, so setting one would have moved the other on its next poll and an
  operator would watch a value they never touched change on its own. Merged
  to five entities, with `strings.json` and `translations/en.json` following.
- **`SET_I_MIN` had no entity at all.** It is the charge termination current,
  so with CCCV live a charge could not terminate through the HA interface.
  Added.
- The simulator seeded charge and discharge currents to the same two
  addresses. Both were `2.0`, so **the collision was invisible** - the
  simulator would have kept agreeing with a mirror that had the merge wrong.
  This is exactly the silent-mismatch case, and it is why the seeds now use
  distinct values.

### Also found and fixed: the BLE record had drifted

Not in this ToDo's scope, but `tests/test_protocol.py` caught it once the
suite could run: `ble_slot_status_t` grew 68 -> 70 B in ToDo 04 when the
CC/CV regulation flags were appended, and the integration still decoded 68.
Added `bts_const_voltage`/`bts_const_current`, kept `SLOT_STATUS_V3_FMT` so a
proto 3-5 unit still decodes its 68-byte prefix rather than being rejected,
and updated the import-time size assertion - which did its job and failed
loudly rather than misdecoding.

### Tests: the gap that let this happen

The unit block was header-verified from the start. **The per-slot blocks were
not** - their geometry was hard-coded - which is precisely where the v2.1
stride change slipped through unnoticed for two revisions. Closed:

- `test_per_slot_addresses_match_the_c2000` walks all 8 channels and checks
  runtime, settings and calibration addresses against the parsed enum.
- `test_every_unit_and_tuning_address_matches_the_c2000` covers all 40 unit
  and tuning registers, so a future addition cannot be missed by being left
  off a hand-picked list.
- `test_limits_addresses_are_distinct` pins the merge directly.
- `test_map_is_dense` records that there is no reserved padding, contradicting
  a stale comment in `registers.h` about "generous strides".
- `test_cal_telemetry_base_follows_the_c2000` now derives from the header
  instead of hard-coding 1220/1224, and its `xfail` on ESP32 drift became a
  hard assertion - that drift is fixed and all three copies now agree.
