## CPU2 drops host register writes that arrive faster than CPU1 drains them

**Status: open.** Found on the bench 2026-10-14. Worked around on the ESP32
(write pacing, see "Workaround in place" below); the C2000 itself is unchanged.

### Symptom

A charge started from the ESP32's front panel did nothing. The screen said
"Charging", the slot LED never changed, and the slot never ran. The same charge
sent over the AT console worked: 1.00 A into a shorted socket, status RUNNING +
CHARGING + CC.

Watching slot 1's registers over AT while the panel started a charge, twice:

| Time | `C0M` (mode) | `C0S` (status) | |
|---|---|---|---|
| 4.7 s | **3** (run + charge) | 2 (stopped) | mode written |
| 7.6 s | 3 | 3 / 2 | never reaches RUNNING |
| 8.0 s | 0 | 2 | ESP32 gives up |

The mode register reads 3 - the write reached `registers[]` - but CPU1 never
acted on it.

### Cause

Three facts, each confirmed in source:

1. **The mailbox has one slot, and a full one drops the new write.**
   `notifyCpu1RegisterWrite()` (`com_cpu2.c`) returns without sending if
   `BTS_IPC_FLAG_REG_WRITE` is still busy:

   ```c
   if (IPC_isFlagBusyLtoR(IPC_CPU2_L_CPU1_R, BTS_IPC_FLAG_REG_WRITE)) {
       return;
   }
   ```

   `applyHostRegisterWrite()` has already put the value in `registers[]`, so a
   read-back looks correct. Only the hand-off to CPU1 is lost.

2. **CPU1 empties it slowly.** `BTS_HandleRegisterWrite()` runs only from task
   B3, one third of the B rotation - about every 15 ms at `TASKB_FREQ_HZ`
   200 Hz.

3. **CPU1 acts on the mode from the mailbox, not from `registers[]`.**
   `BTS_HandleRegisterWrite()` calls `modeCallback(ipcMsg.value, channel)`.
   Nothing re-reads `registers[]` for a mode later, so a dropped mode hand-off
   is gone for good.

The ESP32's `start_power()` writes the five slot limits (V_MIN, V_MAX, I_MIN,
I_MAX, MAX_CELL_TEMP) and then the mode, back to back - six I2C transactions in
about 6 ms. The mailbox is still holding an earlier limit when the mode
arrives, so the mode is the write dropped. Over AT the limit and the mode were
separate commands tens of milliseconds apart, so the mailbox had drained.

**Any host writing quickly loses writes this way**: BLE, HTTP, the HA
integration's register writes, CAN, and a script on the AT console. A dropped
limit write is silent too - CPU1 keeps the old limit until the next mode
command re-latches it.

### Fix

Do one of these in the C2000 - the first is preferred.

1. **Make CPU1 act on the register file, not the message.** CPU2 is already the
   sole writer of `registers[]` and updates it before raising the flag. Turn the
   mailbox into a doorbell: CPU2 sets a per-slot "settings changed" bit (or a
   bitmap over the settings region) instead of overwriting `ipcMsg`, and
   `BTS_HandleRegisterWrite()` re-reads `registers[]` for every flagged slot.
   Nothing is lost when writes arrive faster than B3 runs, and the latest value
   always wins. Edge commands (pause 0x08, resume 0x10, clear fault 0x40,
   waiting 0x20) need care: a later plain write must not erase an edge that has
   not been acted on yet - give them their own pending bits.
2. **Queue the writes.** Replace the single `ipcMsg` with a small ring in
   `CPU2TOCPU1RAM` (CPU2 the only producer, CPU1 the only consumer, head/tail
   indices). Sixteen entries of {index, value} is 64 words, inside the 304
   words free. When the ring is full, CPU2 must still not drop silently:
   NACK the I2C write, or count drops in a register the host can read.

Either way:

- **Count drops.** Add a diagnostic register (or reuse a spare unit register)
  that increments whenever a host write is not delivered to CPU1, so this
  failure can never be invisible again.
- **Check the other single-slot flags.** `BTS_IPC_FLAG_TEMP_UPDATE`,
  `CAL_RELOAD` and `STATE_RESTORE` use the same busy-then-skip pattern. Most are
  advisory, but confirm none can lose something that matters.
- **Rebuild and load BOTH cores** - the IPC contract changes on both sides.

### Workaround in place (ESP32)

`esp32-btle-proxy/components/bts_link/bts_link.c` paces every register write:
`bus_write_reg()` waits until `BTS_WRITE_GAP_MS` (30 ms, two B3 periods) has
passed since the previous write. Reads are not paced. On top of that,
`test_engine.c` re-sends a start once if the slot is not RUNNING a second after
the mode went out (`retry_unstarted()`).

Once the C2000 is fixed, the pacing can come out - set `BTS_WRITE_GAP_MS` to 0
and leave the retry in, it is harmless.

### Verify

1. With the ESP32 pacing set to 0, start a charge from the front panel: the slot
   must reach RUNNING + CHARGING on the first try.
2. Write the five limits and the mode in one I2C burst from a script; all six
   must take effect (read back the converter's behaviour, not just
   `registers[]`).
3. The drop counter must stay at 0 under both tests.
