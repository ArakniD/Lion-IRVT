## Changelog — COMPLETE

**Status: DONE.** Compile-verified on both cores. **No hardware this session**
— nothing below has been observed running on a board.

### 1. ADC to 99.67 kSPS, 1:1 with EPWM1

`BTS_ADC_SOC_PRESCALE` 15 → 1 (`bts_user_settings.h`). The SOC event
prescaler is the only divider in the path — EPWM1's TBPRD belongs to channel
1's converter and is rewritten after the trigger setup, so it cannot be used
to set the sample rate. 99.67 kHz / 1 = **99.67 kSPS**.

### 2. The C28x taken out of the fast path

An ADCA INT1 every 10.03 µs would land on a core already servicing eight
ADS131M08 DRDY control loops, so:

- `Interrupt_disable(INT_ADCA1)` in `main()` — the ISR stays *registered*, so
  a bring-up build restores it by deleting one line, but it never fires.
- `ADC_enableContinuousMode(ADCA_BASE, ADC_INT_NUMBER1)` in
  `BTS_HAL_setupADC()`, so the converter does not stall waiting on an
  acknowledgement that will never come.

### 3. CLA filters retuned, and a second filter added

`Cla1Task1` now runs **two** IIRs per channel:

| Filter | alpha | Derivation | Consumer |
|---|---|---|---|
| `...Filt` | 0.0012608 | `2*pi*20/99670` | 20 Hz telemetry (was 0.018912 at 6.645 kSPS; the corner is unchanged) |
| `...Fast` | 0.22222 | `2/(N+1)`, N = 8 | the protection path |

The fast pair is not a refinement — it is **required** by item 2. With the ISR
masked, `CellVoltage_16b[]` is never written, so `CellVoltage_V` would have
frozen at its last value and the reverse-polarity check would have gone on
trusting it. `BTS_refreshCellFromCla()` (called first in `C1()`) re-sources
that pair from the fast filter; `BTS_cellVoltageAsCtrl16b()` reads it too.
`alpha = 2/(N+1)` matches the settling of the 8-sample ring it replaces —
~184 µs here against the 1204 µs the ring spanned at the old rate, so the
protection path is *faster* than before, and refreshed every sweep rather
than once per 100 ms telemetry pass.

If the CLA stops, readings are **left alone rather than zeroed**: a
fabricated 0 V reads as reverse polarity, so a stale value is the safer
failure.

### 4. `BTS_claRunCount` widened to 32-bit — a defect the rate change created

The liveness counter is tested for *inequality against the previous `C1()`
pass*. At 99.67 kSPS a 16-bit counter wraps in **657 ms**, and while `C1()`'s
nominal period is 100 ms, it was **measured on hardware at 0.69 Hz — a
~1.45 s period, longer than the wrap** (see the project note
`bts-cpu1-task-chain-runs-slow`).

So a 16-bit counter could have read the same value on two consecutive passes
with the CLA running perfectly, latched `claFastStale`, stopped
`BTS_refreshCellFromCla()` — and frozen the very readings the counter exists
to protect. At the old 6.645 kSPS the wrap was 9.86 s and the same 1.45 s
period had 6.8× margin, so **this defect did not exist until the rate
changed.** Widened to `uint32_t` (wrap ~12 h) on both sides, with the locals
in `BTS_updateFilteredTelemetry()`. Verified atomic in the generated
assembly: `MMOV32` on the CLA, `MOVL ACC` on the C28x, object at even address
`0xa902`.

### 5. ADCB end-of-conversion flag (the self-contained item)

`updateInputVoltage()` now clears ADCB INT1 on the **success** path as well
as the timeout path, and gates the result read on `adcbTimedOut`. The
bounded-wait guard was dead code from the second call onward — `adcbEocTimeouts`
could never increment, so a genuinely stuck ADCB was indistinguishable from a
healthy one. It is live again.
