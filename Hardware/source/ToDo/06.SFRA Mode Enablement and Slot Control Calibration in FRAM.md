## Mode_[A-C] 0b000 enable SFRA by EN_[A-C] enablement

Each slot can be calibrated for CC and CV control loop with calibration data from the SFRA process. This is currently #define compiled out, but needs to be enabled via the MODE_[A-C] 0b0000 mode-set, with the slot selected for the calibration via the EN_[A-C] slot enablement inputs.

Mode 0b0000 is un-used and shall be use to enable SFRA calibration mode.

In SFRA calibration mode, the AT-Command interface is disabled, and the slot becomes the SFRA serial port for the Ti SFRA calibration tool.

On completion of the SFRA calibration process, the calculated values will be stored in F-RAM, in a section just after the per slot voltage/current calibration, such that it can be done seperately post slot calibration, for slot tuning. The calibration data is calculated externally and must be set via the i2c/api/btle interface register setting process.

Call this feature a slot tuning feature.

We need new registers to store and retrieve slot tuning values, these registers shall go after the unit resigters, at the end of the register mapping as they are not normal run-time registers and only used to store and retrieve slot tuning values during system build, by the system builder. end-users do not perform this slot tuning.

The defaults are below:
#define BTS_DCL_CC_B0                ((float32_t) 0.0331015)
#define BTS_DCL_CC_B1                ((float32_t) -0.0623757)
#define BTS_DCL_CC_B2                ((float32_t)  0.0293372)
#define BTS_DCL_CC_A1                ((float32_t) -1.9605802)
#define BTS_DCL_CC_A2                ((float32_t) 0.9605802)

#define BTS_DCL_CV_KDC               ((float32_t)5000)
#define BTS_DCL_CV_Z0                ((float32_t)0.100)
#define BTS_DCL_CV_Z1                ((float32_t)2.000) // 2
#define BTS_DCL_CV_P1                ((float32_t)2.000) // 2

#define BTS_DCL_CV_B0                ((float32_t) 8.0377472)
#define BTS_DCL_CV_B1                ((float32_t)-13.2244008)
#define BTS_DCL_CV_B2                ((float32_t) 5.2402228)
#define BTS_DCL_CV_A1                ((float32_t)-1.6651931)
#define BTS_DCL_CV_A2                ((float32_t) 0.6651931)

The slot tuning is stored globally on the entire unit, as each slot is the same tuning.

Therefor we have :
DCL_CC_B[0-2]
DCL_CC_A[1-2]
DCL_CV_Z[0-1]
DCL_CV_P[1]
DCL_CV_B[0-2]
DCL_CV_A[1-2]

All float32, defaults above.

On boot, these values are read from f-ram, along with calibration and restart memory, and applied to the CC and CV control loops.

## Changelog - PART 1 COMPLETE (slot tuning registers)

**Status: the tuning registers are DONE. The runtime SFRA switch is NOT, and
is filed as ToDo 07.** Split on the user's instruction, because the two halves
are independent and only the registers fit the session.

Compile-verified on both C2000 cores and the ESP32. **No hardware.**

### What landed

**13 tuning registers at 1068-1116**, appended above the unit block:
`DCL_CC_B0..B2/A1/A2`, `DCL_CV_Z0/Z1/P1`, `DCL_CV_B0..B2/A1/A2`.
`TOTAL_REGISTERS` 267 -> 280.

The spec listed these as the defaults to carry. Note they are **not** the
values currently compiled in: `bts_user_settings.h` selects a different CC set
via an `#if/#elif` chain, and a different CV_Z1/P1 pair. The seeding function
takes whatever `BTS_DCL_*` resolve to at build time rather than the literals
in this ToDo, so the defaults match the firmware that ships with them.

**One set for the whole unit**, as specified - every slot is the same
converter. No per-slot stride.

**Z0/Z1/P1 are carried but never read by the firmware.** The DCL runs the
biquad coefficients directly. They record what the coefficients were derived
from so a later re-derivation has the design intent.

**F-RAM record at 0x0700**, 128 B: header `0xA571`, 13 floats, CRC-32. Placed
after the slot-state region that ends at 0x06FF - checked deliberately, since
a previous F-RAM addition collided with the global voltage thresholds.

**Applied at boot and on every host write.** CPU2 restores the record and
raises the existing CAL_RELOAD flag; CPU1 calls `BTS_applySlotTuning()` from
the same handler that reloads calibration. A host write to any coefficient
re-applies the whole block - the biquad is only meaningful as a set, and
writing five coefficients one at a time would otherwise run four passes with a
mixed tuning installed.

### The failure this is guarded against

`registers[]` starts zeroed, and **a biquad with every coefficient zero
produces a constant zero output** - the duty never leaves its floor and no
slot regulates at all. A silent, total loss of control originating in a
register block most users never touch.

Two guards: `BTS_seedSlotTuningRegisters()` runs on CPU1 before CPU2's F-RAM
restore can arrive, and `BTS_applySlotTuning()` rejects a set whose `b0` is
zero and re-seeds. A never-tuned unit, or one whose record fails its CRC, runs
the shipped tuning.

### Decode branch on CPU1 - not optional

The tuning block sits above the unit registers, so without an explicit branch
in the IPC register-write handler the index falls outside every existing test,
the flag is acked, and the write is **accepted by CPU2 and silently dropped**:
`registers[]` would show the new coefficient while the controllers kept the
old one. This is the same trap the calibration block hit previously.

### Also fixed in passing

`bts_regs.h`'s REGIONS comment still described the **v1** map (settings stride
96, unit base 1152) long after the values below it moved to v2.1. The
`#define`s were correct; only the comment was stale. Corrected, and the tuning
region added. ToDo 05 had flagged this.

### Verification

- CPU1 via `buildProject`: `"errors": []`, `"success": true`.
- CPU2 via the approved gmake: linked. One real error caught and fixed -
  `loadSlotTuning()` was called ~170 lines above its definition and needed a
  forward declaration; it linked only after that.
- All eight shared symbols identical in both maps.
- **Message RAM: `CPU2TOCPU1RAM` 0x2b6 -> 0x2d0, exactly the 26 words the 13
  floats need, with 304 free.** This block is the binding constraint on new
  shared registers, so it was checked rather than assumed.
- ESP-IDF `idf.py build`: clean, 41% of the app partition free.

### Not verified - needs hardware

- That a tuning written over I2C/BLE survives a power cycle.
- That the CRC rejects a corrupted record rather than installing it.
- That the zero-`b0` fallback actually fires, which by design should never be
  observed on a healthy unit.

## NOT DONE - the runtime SFRA switch (see ToDo 07)

The second half of this ToDo - MODE `0b000` selecting SFRA mode at runtime,
the AT console becoming the SFRA serial port, and `BTS_SFRA_ENABLED` moving
from compile-time to runtime - is **not implemented**. It touches ~20 `#if`
sites including the control-ISR injection points and takes SCIA away from the
console and LED driver at runtime, which is more than the session allowed.

**It is also blocked on a design conflict, recorded in ToDo 07:** this ToDo
says MODE `0b000` is unused, but `registers.h` maps mode 0 to
`eModeIndependent` (8 independent slots), and the MODE/ENABLE straps are
pulled high, so an **unstrapped unit decodes through `truth_table[7]` to mode
0**. Taking mode 0 for SFRA would put every unstrapped board into calibration
mode at power-on. The mode table needs a decision before that half can be
built.

One thing was done for it here: `BTS_SFRA_CAPTURE_SETTINGS` is now defined in
the CCCV branch of `bts_user_settings.h` (done in ToDo 04). It was missing,
and turning SFRA on would have failed to compile with the macro silently
evaluating to 0.
