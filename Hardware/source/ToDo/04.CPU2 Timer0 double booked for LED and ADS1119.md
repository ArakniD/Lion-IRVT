## Changelog - COMPLETE

**Status: DONE.** Compile-verified on both C2000 cores and on the ESP32.
**No hardware this session** - nothing below has been seen running.

### 1. LED timer moved to CPU Timer 2 (CPU2)

The double-booking was worse than this ToDo described. `initADS1119()`
reprograms Timer 0 to a free-running `0xFFFFFFFF` period with **the interrupt
disabled**, and `main()` calls it *after* `LEDDriver_init()` - so in any
production build (`BTS_LED_DRIVER_ENABLED == true`) the ADS1119 setup silently
switched the LED tick off moments after it started. **The WS2812B string was
dead in every production build**, having briefly worked at boot.

Fixed by moving the LED dwell to Timer 2 rather than guarding the ADS1119
setup: the dwell genuinely needs a free-running counter in both build
flavours, and Timer 2 has no other claimant on CPU2.

**The ACK-group line had to be deleted, not carried over.** `INT_TIMER0` is a
PIE interrupt (1.7); `INT_TIMER2` reaches the CPU directly on INT14. Keeping
`Interrupt_clearACKGroup(INTERRUPT_ACK_GROUP1)` would have re-opened PIE group
1 - which carries the ADC interrupts - from a handler that never arrived
through it. Both the live body and the `#else` stub lost the call.

Timer 2 is free **on CPU2 only**. On CPU1 it is the Task C timebase and is
borrowed by `BTS_HAL_measureSysclkKHz()`; CPU2 runs neither.

### 2. CCCV control mode

`BTS_LAB_TYPE` -> `BTS_LAB_CLOSED_LOOP_CCCV`. The CV half of `BTS_ctrlISR()`
was already written and had been compiled out since the beginning. Three
things that looked like separate omissions were all that one setting:

- `iref_cuttout_A`, loaded from `I_MIN` and shared across a group, was read by
  nothing.
- `status[].finished` (bit 2, END) was published but never set by any path.
- `ctrlMode_logic` was pinned to 0, so status bits 6/7 read "always CC".

Also defined `BTS_SFRA_CAPTURE_SETTINGS` in the CCCV branch. It was missing,
which is invisible now because the block that uses it sits inside
`#if(BTS_SFRA_ENABLED == true)` - but ToDo 06 turns SFRA on, and it would have
failed there with the macro silently evaluating to 0.

### 3. Termination - `serviceTermination()`

Runs in `C1()`, before the group-integrity check.

| Direction | Ends when | Disabled by |
|---|---|---|
| Charge | **in CV** and `abs(I) <= I_MIN` | `I_MIN == 0` |
| Discharge | `V <= V_MIN` | **`V_MIN == 0`** |

The CV requirement is load bearing: current ramps from zero at the start of a
charge, so `abs(I)` is below `I_MIN` at the moment the slot starts, and an
unguarded test would end every charge immediately.

Sensor is the **ADS131M08** (`Isense_A`/`Vsense_V`) - the converter the CC
loop regulates against and the counters integrate, and live for every MODE
strap, unlike the internal-ADC pair.

Both conditions must hold for `BTS_TERM_DWELL_PASSES` (5) consecutive passes.
Expressed in passes rather than seconds because C1 is nominally 10 Hz but was
measured at 0.69 Hz: ~0.5 s nominal, ~7 s measured.

In a group only the **leader** decides and it ends the whole group; followers
mirror its duty and run no controller. `slotFinish()` is distinct from
`slotStop()` - same shutdown, but `finished` set and `stopped` clear, so a
completed test is distinguishable from a halted one.

### 4. Linker: the ISR code region had to grow

**This is the part that would not have been predicted.** CCCV pulled the CV
branch into `BTS_ctrlISR()`, which is `FUNC_ALWAYS_INLINE` and expands into
all eight per-channel ISRs. `isrcodefuncs` went from `0x1c7c` to `0x22b1` and
**the link failed outright** - run placement against the `0x2000` RAMGS9_10
region, and then load placement against the `0x2000` FLASHC sector, which the
linker reports separately.

- RUN: `RAMGS9_10` -> `RAMGS8_9_10` (`0x014000`, `0x3000`). RAMGS8 was directly
  below and completely empty; the `Filter*_RegsFile` sections nominally there
  are unreferenced reference-design leftovers that allocate nothing.
- LOAD: `FLASHC` -> `FLASHE` (`0x8000`, held only an empty `.init_array`).

Final: `0x22b1` used of `0x3000` RAM (`0xd4f` spare) and of `0x8000` flash.
This is GSx silicon, but the group is code copied from flash at boot and CPU2
places nothing above RAMGS11, so the RAMGS0 flash-algorithm hazard does not
reach it.

### 5. CC/CV to the hosts

Bits 6/7 and their ESP32 masks already existed; nothing decoded them by name.
Added `const_voltage`/`const_current` through `bts_link` -> `test_engine` ->
web API (`bts.const_voltage`/`const_current`), BLE and the display.

- **BLE**: two `uint8_t` appended at the **end** of `ble_slot_status_t`,
  68 -> 70 B, `BLE_PROTO_VERSION` 5 -> 6. Every existing offset is unchanged.
  `tools/ble_verify.py` updated to match and its `MIN_PROTO_VERSION` raised
  3 -> 6, since it now unpacks 70 bytes and a proto-5 unit returns 68.
- **Display**: `CC`/`CV` in the gap between the slot number and the voltage
  column, cyan for CV. Nothing is drawn for a slot that is not running.
- `test_engine.c` now reads the decoded field instead of re-masking
  `status_bits`. Its comment already anticipated "a BTS build that does not
  publish the CV status bit" - that fallback is now backed by real firmware.

## Superseded, 2026-10-02 — the LEDs were never going to light

Item 1 of this ToDo is now **historical**. The Timer 2 move was a real fix to
a real defect, and the analysis of the double-booking was correct: a timer
whose interrupt `initADS1119()` silently disabled genuinely could not tick.

But it could never have lit the string, and neither could anything else on
SCIA.

`LEDDriver_update()` clocked **raw colour bytes out of a UART at 800 kbaud**.
A WS2812B decodes pulse *widths* — 400 ns high is a 0, 800 ns high is a 1,
inside a 1250 ns slot. A UART cannot produce them: it forces a LOW start bit
before every byte and holds each data bit for a full bit time. The strip saw
framing noise and latched nothing. **No pixel ever lit from the C2000**, in
any build, at any point in the project's life.

That is why "the LEDs now tick" sat unverified under *Not verified — needs
hardware* above, and why two further fixes in the same area — the LED ISR
starving CPU2's I2C target, and SCIA being stranded by an unstrapped MODE
strap — each corrected something real without ever producing light.

Driving a WS2812B needs a peripheral that emits a free-running bit pattern,
i.e. SPI, and the C2000 has none to give: GPIO29 — the wire that physically
exists — has no SPI mux option, and both usable SPI ports are held by the
ADS131M08 pair.

**The function moved to the ESP32** (commit `bd48bfd`), which has a spare SPI
host and already polls slot status over I2C. It lit on the first attempt:
eight solid green, all slots idle.

Consequences for this ToDo's subject matter:

- `BTS_LED_DRIVER_ENABLED` is `false` in **both** arms of the build switch.
- `ledTimerISR` is registered nowhere, so **CPU Timer 2 on CPU2 is free
  again**. Timer 0 remains the ADS1119 dwell's alone, as this ToDo left it.
- The Timer 0 analysis, the Timer 2 ownership table and the
  direct-INT14-must-not-ACK rule all remain correct and are still worth
  reading. Only the claim that fixing them would light the string was wrong.

Item 2 of this ToDo — the CCCV switch and `serviceTermination()` — is
unaffected.
